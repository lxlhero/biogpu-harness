# BioGPU-Harness 使用方式优化方案

> 目标：优化 `/bio-gpu-team` 的用户入口体验。
> 当前问题：A/B 模式启动方式不统一，B 模式需要传配置路径；A 模式询问过多工程细节。
> 新目标：所有任务统一从 `/bio-gpu-team` 无参数启动，先问工具名，再问任务模式，再问少量业务需求。工程细节交给 agents 自动处理。

---

## 一、当前问题

当前 README.md 中的使用方式是：

```bash
cd /Users/huron/code/ai_lab/biogpu-harness
claude
/bio-gpu-team
```

A 模式：

```text
1. 启动 /bio-gpu-team
2. 检测到无项目配置
3. 自动调用 /bio-gpu-project-init
4. 按向导填写工具信息
```

B 模式：

```bash
/bio-gpu-team /Users/huron/code/ai_lab/transfer2gpu/<tool_name>/biogpu_project.yaml
```

或者：

```text
/bio-gpu-team
> workspace_path: /Users/huron/code/ai_lab/transfer2gpu/scavenge
```

这个设计有几个问题：

```text
1. A/B 模式入口不统一。
2. B 模式像“传配置文件启动”，不是“业务任务入口”。
3. 用户不能自然表达这次要修复什么、优化什么、继续什么。
4. A 模式问得太细，比如源码路径、精度要求、CPU baseline、rjob/Docker，这些不应该由用户入口阶段决定。
5. README.md 应该是用户使用说明，不应该写过多内部架构和工程细节。
```

---

## 二、新的统一使用方式

无论是新工具，还是已有工程继续修复/优化，都统一这样启动：

```bash
cd /Users/huron/code/ai_lab/biogpu-harness
claude
/bio-gpu-team
```

不要在 README.md 主流程中推荐：

```bash
/bio-gpu-team /path/to/biogpu_project.yaml
```

这个可以作为高级兼容用法保留在内部文档，但不作为用户主要使用方式。

## 三、新的 `/bio-gpu-team` 启动向导

### 3.1 第一步：先问工具名称

`/bio-gpu-team` 启动后第一步必须问：

```text
请先告诉我这次要处理的生信工具名称。

例如：
- gsMap
- scavenge
- susieR
- 自定义工具名
```

原因：

```text
BioGPU-Harness 的核心对象是“某个生信工具”。
用户首先知道自己要处理哪个工具，然后才决定是从头加速还是修复已有工程。
```

不要第一步就问 A/B 模式。

---

### 3.2 第二步：选择任务模式

用户输入工具名后，再问：

```text
请选择这个工具的任务模式：

A. 从头开始 GPU 加速这个工具
B. 修复 / 优化 / 继续这个工具的已有 GPU 加速工程
```

## 四、A 模式：从头开始 GPU 加速

### 4.1 A 模式只问少量业务问题

如果用户选择 A，只问以下问题：

```text
1. 本次 GPU 加速目标是什么？
   可自由描述，例如：
   - 做端到端 GPU 加速
   - 先自动分析瓶颈，优先加速最值得做的模块
   - 希望整体速度至少提升 2x
   - 只加速某个指定模块
   - 优先保证结果和原工具一致

2. 是否指定工具版本或下载来源？
   - 没有：由 agent 自动查找、下载、初始化
   - 有：用户可以提供 GitHub / GitCode / pip / conda / release 版本等信息

3. 是否有希望优先使用的数据集或 benchmark？
   - 没有：由 agent 自动选择或构造 profiling benchmark 和 primary_e2e benchmark
   - 有：用户提供路径或说明

4. 工作区是否使用默认路径？
   默认：
   /Users/huron/code/ai_lab/transfer2gpu/<tool_name>

   - 是：直接使用默认路径
   - 否：用户提供自定义 workspace_path
```

A 模式不要再问：

```text
1. 生信工具源码路径在哪里？
2. 是否已有 CPU baseline？
3. 精度要求是什么？
4. 是否使用 rjob / Docker / 集群？
```

---

### 4.2 为什么不问源码路径

A 模式是“从头开始”。用户只提供工具名，agent 应该自己完成：

```text
1. 查找工具来源
2. 下载 / clone / install 工具
3. 初始化 bio_tool_path
4. 写入 source_setup_report.md
```

如果用户确实有指定源码或版本，就在“是否指定工具版本或下载来源？”里提供。

---

### 4.3 为什么不问精度要求

精度要求不应该由用户在入口阶段手动定义。
不同生信工具输出差异很大，应该由 `bio-gpu-test-planner-agent` 根据工具输出自动判断。

例如：

```text
1. exact match
2. numerical tolerance
3. ranking consistency
4. correlation
5. RMSE / MAE
6. Jaccard / top-k overlap
7. statistical equivalence
8. domain-specific metric
```

`bio-gpu-test-planner-agent` 必须在测试计划阶段自动生成：

```text
reports/test_plans/primary_e2e_test_plan.md
```

其中包含：

```text
1. benchmark 输入
2. CPU command
3. GPU command
4. precision_metrics
5. speed_metrics
6. pass/fail threshold
7. 为什么选择这些精度指标
```

然后交给用户确认。

也就是说：

```text
用户不在入口阶段定义精度。
agent 在 test plan 阶段判断精度。
用户只确认 test plan。
```

---

### 4.4 为什么不问 CPU baseline

A 模式默认没有 CPU baseline。
CPU baseline 应该由：

```text
bio-gpu-test-runner-agent
```

在 primary_e2e 阶段建立。

---

### 4.5 为什么不问 rjob / Docker / 集群

rjob / Docker / 集群属于执行环境策略，不是用户入口问题。
默认由：

```text
harness_config.yaml
configs/image_config.yaml
configs/rjob_config.yaml
bio-gpu-image-builder-agent
bio-gpu-test-runner-agent
```

判断和使用。

如果执行过程中发现必须使用 rjob / Docker，再由对应 agent 提醒用户确认。

## 五、B 模式：修复 / 优化 / 继续已有工程

### 5.1 B 模式也从 `/bio-gpu-team` 无参数启动

用户不要再主流程里这样启动：

```bash
/bio-gpu-team /path/to/biogpu_project.yaml
```

而是统一：

```bash
/bio-gpu-team
```

然后：

```text
1. 输入工具名称
2. 选择 B 模式
3. 提供已有工程路径
4. 描述本次要修复或优化什么
```

---

### 5.2 B 模式向导问题

如果用户选择 B，只问这些：

```text
1. 这个工具的已有工程工作区在哪里？
   默认尝试：
   /Users/huron/code/ai_lab/transfer2gpu/<tool_name>

2. 这次具体要做什么？
   请选择或自由描述：

   a. 修复精度不达标
   b. 修复 E2E 测试失败
   c. 修复 module test 失败
   d. 修复运行错误 / rjob 错误 / Docker 错误
   e. 优化速度，当前能跑但速度不满意
   f. 继续做下一个 GPU 加速模块
   g. 重新设计或补跑 benchmark
   h. 补做用户 double-check benchmark
   i. 生成或更新最终报告
   j. 其他，自由描述

3. 是否允许 agent 修改已有 GPU 代码？
   默认：允许，但必须先生成 execution_plan.md 供用户确认。

4. 是否需要在执行前确认 execution_plan.md？
   默认：需要。
```

B 模式不要一上来问：

```text
1. 是否沿用已有 benchmark？
2. 是否沿用已有 baseline？
3. 是否沿用已有 GPU 实现？
4. 是否允许重新 profiling？
```

这些应该由 `bio-gpu-existing-project-planner-agent` 扫描 artifacts 后判断，并写入 `execution_plan.md`。

## 六、需要修改的 agent 职责

这次优化不是只改 README，还需要同步修改 agents 的任务边界。

---

### 6.1 `/bio-gpu-team` 修改

文件：

```text
.claude/commands/bio-gpu-team.md
```

职责调整为：

```text
1. 永远作为统一入口启动。
2. 不再优先要求用户传 biogpu_project.yaml。
3. 第一问：工具名称。
4. 第二问：A/B 模式。
5. A 模式：只采集少量业务目标。
6. B 模式：采集 workspace_path 和本次修复/优化需求。
7. 根据模式调用 /bio-gpu-project-init 或 bio-gpu-existing-project-planner-agent。
8. 不直接处理精度策略。
9. 不直接处理源码下载。
10. 不直接判断是否重跑 benchmark/baseline/profiling。
```

新的启动逻辑：

```text
/bio-gpu-team
→ ask tool_name
→ ask mode A/B

if mode = A:
  → ask acceleration_goal
  → ask optional source/version
  → ask optional benchmark/dataset
  → ask workspace default yes/no
  → call /bio-gpu-project-init(mode=A)
  → next_action = setup_source_or_benchmark

if mode = B:
  → ask existing workspace_path
  → ask session_request
  → ensure biogpu_project.yaml/task_state.json exists
  → write task_state.session_request
  → next_action = plan_existing_project
  → call bio-gpu-existing-project-planner-agent
```

### 6.2 `/bio-gpu-project-init` 修改

文件：

```text
.claude/commands/bio-gpu-project-init.md
```

职责调整为：

```text
1. 负责创建或补全工作区结构。
2. A 模式不要求用户提供源码路径。
3. A 模式写入 source.status = pending。
4. A 模式写入 precision.policy = auto。
5. B 模式不覆盖已有 reports/runs/baseline。
6. B 模式缺少配置时补建配置。
```

A 模式初始化后，`biogpu_project.yaml` 应包含：

```yaml
tool_name: <tool_name>
mode: A

harness:
  root: /Users/huron/code/ai_lab/biogpu-harness

  workspace_path: /Users/huron/code/ai_lab/transfer2gpu/<tool_name>

source:
  status: pending
  user_specified_source: false
  source_url: null
  version: null
  install_method: auto

  summary: "<用户自由描述的 GPU 加速目标>"

benchmarks:
  primary_e2e:
    status: not_ready
    source: harness_selected
    name: null
    path: null
    input_manifest_path: null
  double_check_e2e:
    status: not_requested
    source: user_provided
    name: null
    path: null
    input_manifest_path: null

  policy: auto
  decided_by: bio-gpu-test-planner-agent
  plan_path: null
```

B 模式必须写入或更新 `task_state.session_request`。

### 6.3 `bio-gpu-benchmark-agent` 修改

文件：

```text
.claude/agents/bio-gpu-benchmark-agent.md
```

新增职责：

```text
1. A 模式下，如果 source.status = pending，则根据 tool_name 和 source 字段自动查找工具来源。
2. 如果用户提供 source_url/version，则优先使用用户指定来源。
3. 如果用户没有提供来源，则自动查找 GitHub/GitCode/pip/conda/release 信息。
4. 下载或初始化源码到 bio_tool_path。
5. 生成 reports/source_setup_report.md。
6. 更新 biogpu_project.yaml:
   source.status = ready / failed
   source.source_url = ...
   source.version = ...
   source.install_method = ...
7. 设计 profiling benchmark。
8. 设计 primary_e2e benchmark。
9. 不要求用户提供源码路径。
```

如果无法确定工具来源，agent 应该返回：

```text
status = blocked
blocker = need_user_source
question = 请提供该工具的官方仓库、安装方式或源码压缩包路径
```

只有在自动查找失败后，才向用户补问来源。

### 6.4 `bio-gpu-test-planner-agent` 修改

文件：

```text
.claude/agents/bio-gpu-test-planner-agent.md
```

新增职责：

```text
1. 自动判断精度指标，不要求用户入口阶段提供 precision requirement。
2. 根据工具输出类型选择 precision_metrics。
3. 生成 pass/fail threshold。
4. 在 test_plan 中解释为什么选择这些指标。
5. 将 precision.policy 从 auto 更新为 planned。
6. 将 precision.plan_path 写入 biogpu_project.yaml。
```

它必须分析：

```text
1. 工具输出文件类型
2. 输出是否 deterministic
3. 输出是否数值型
4. 输出是否排序/集合/图/矩阵/统计结果
5. CPU baseline 输出
6. 生信任务领域习惯
```

示例规则：

```text
1. 完全确定性文本输出 → exact match / checksum
2. 浮点矩阵/向量 → abs/rel tolerance + correlation
3. ranking / enrichment 结果 → top-k overlap + Spearman
4. peak/cell/gene 集合 → Jaccard / F1
5. 概率或统计模型 → distribution-level comparison
6. 非确定性算法 → seed 固定 + statistical equivalence
```

输出：

```text
reports/test_plans/<test_suite>_test_plan.md
```

必须包含：

```text
precision_metrics
speed_metrics
pass_threshold
rationale
user_approval_required = true
```

---

### 6.5 `bio-gpu-test-runner-agent` 修改

文件：

```text
.claude/agents/bio-gpu-test-runner-agent.md
```

职责保持 planner/runner 分离：

```text
1. 只执行 test_plan。
2. 不重新发明 precision_metrics。
3. 如果 test_plan 缺少 precision_metrics，则返回 planner 修复。
4. A 模式中负责建立 CPU baseline。
5. GPU compare 阶段负责运行 GPU 版并比较结果。
6. 将结果写入 reports/test_results/。
```

---

### 6.6 `bio-gpu-existing-project-planner-agent` 修改

文件：

```text
.claude/agents/bio-gpu-existing-project-planner-agent.md
```

B 模式中它负责判断工程细节，不让用户在入口回答一堆问题。

必须读取：

```text
1. biogpu_project.yaml
2. state/task_state.json
3. state/task_state.json.session_request
4. reports/
5. runs/
6. baseline/
7. logs/
8. pitfalls/
```

必须自动判断：

```text
1. 是否已有 benchmark
2. 是否已有 CPU baseline
3. 是否已有 GPU 实现
4. 是否需要重新 profiling
5. 是否需要重跑 primary_e2e
6. 是否需要重跑 double_check_e2e
7. 是否需要修改代码
8. 是否需要重新生成最终报告
```

生成：

```text
reports/execution_plan.md
```

内容必须围绕用户本次需求，而不是只根据已有状态猜。

例如：

```text
如果 session_request.request_type = optimize_speed：
  优先检查 profiling_report、primary_e2e_compare_report、module speedup、端到端瓶颈。
  判断是否需要重新 profiling 或继续优化指定模块。

如果 session_request.request_type = fix_accuracy：
  优先检查 precision report、失败样例、CPU/GPU 输出差异。
  判断是否回到 problem-analyst 或 dev-agent。

如果 session_request.request_type = run_double_check：
  优先检查 primary_e2e 是否已 pass。
  如果 pass，则进入 double_check_e2e planning。
```

## 七、task_state.json 新增 session_request

B 模式必须新增：

```json
{
  "session_request": {
    "tool_name": "scavenge",
    "mode": "B",
    "request_type": "optimize_speed",
    "summary": "scavenge 已经交付，但希望重新检查是否还有端到端加速空间",
    "user_notes": "",
    "allow_code_changes": true,
    "requires_execution_plan_approval": true
  }
}
```

`request_type` 可选：

```text
from_scratch
fix_accuracy
fix_e2e_failure
fix_module_test_failure
fix_runtime_error
fix_docker_or_rjob
optimize_speed
continue_next_module
rerun_benchmark
run_double_check
write_final_report
other
```

注意：

```text
session_request 是“本次任务需求”。
user_request 是“项目长期需求”。
```

## 八、README.md 定位

`README.md` 是用户使用说明，不是架构设计文档。

README.md 应该只回答：

```text
1. 这个项目是什么
2. 怎么启动
3. A 模式怎么用
4. B 模式怎么用
5. 用户需要准备什么
6. 输出在哪里
7. 常见用法示例
```

README.md 不应该详细写：

```text
1. 13 个 agent 的完整职责
2. task_state 全字段
3. 所有目录内部细节
4. schema / hooks / scripts 规划
5. 第二阶段工程化细节
```

这些应该放在：

```text
docs/architecture/
docs/usage/
```

## 九、README.md 推荐内容

将 README.md 改成如下用户说明结构：

````markdown
# BioGPU-Harness

BioGPU-Harness 是一个用于生信工具 GPU 加速的 Claude Code agent harness。

它负责自动完成：

- 工具源码获取和初始化
- benchmark 设计
- CPU baseline 建立
- profiling 和瓶颈分析
- GPU 实现规划
- GPU kernel / 模块开发
- 精度和性能验证
- 用户 double-check benchmark
- 最终报告生成

## 启动方式

所有任务都统一从 `/bio-gpu-team` 启动：

```bash
cd /Users/huron/code/ai_lab/biogpu-harness
claude
/bio-gpu-team
````

启动后，系统会先询问工具名称，例如：

```text
gsMap
scavenge
susieR
```

然后选择任务模式：

```text
A. 从头开始 GPU 加速这个工具
B. 修复 / 优化 / 继续这个工具的已有 GPU 加速工程
```

## A 模式：从头开始 GPU 加速

适用于未做过 GPU 加速的新工具。

A 模式只需要用户提供：

1. 工具名称
2. 本次 GPU 加速目标
3. 可选：指定工具版本或下载来源
4. 可选：指定 benchmark / 数据集
5. 可选：是否使用默认工作区路径

不需要用户提供源码路径。
BioGPU-Harness 会自动查找、下载、初始化工具源码。

不需要用户手动定义精度要求。
BioGPU-Harness 会在测试计划阶段自动选择精度指标，并在执行前交给用户确认。

## B 模式：修复 / 优化已有工程

适用于已有 `transfer2gpu/<tool_name>` 工作区的项目。

B 模式只需要用户提供：

1. 工具名称
2. 已有工作区路径
3. 本次要修复或优化的目标

例如：

* 修复精度不达标
* 修复 E2E 测试失败
* 优化速度
* 继续下一个 GPU 加速模块
* 补做用户 double-check benchmark
* 生成最终报告

系统会扫描已有 artifacts，生成：

```text
reports/execution_plan.md
```

用户确认后再继续执行。

## 工作区位置

默认每个工具的工作区在：

```text
/Users/huron/code/ai_lab/transfer2gpu/<tool_name>
```

runtime artifacts 会写入工具工作区：

```text
reports/
runs/
baseline/
logs/
benchmarks/
artifacts/
```

不会写入 `biogpu-harness` 仓库本身。


---

### 11.2 A 模式验收

A 模式不能再问：

```text
1. 生信工具源码路径在哪里？
2. 是否已有 CPU baseline？
3. 精度要求是什么？
4. 是否使用 rjob / Docker / 集群？
```

A 模式只允许问：

```text
1. 本次 GPU 加速目标是什么？
2. 是否指定工具版本或下载来源？
3. 是否有希望优先使用的数据集或 benchmark？
4. 工作区是否使用默认路径？
```

初始化后的 `biogpu_project.yaml` 必须包含：

```yaml
source:
  status: pending
  install_method: auto

precision:
  policy: auto
  decided_by: bio-gpu-test-planner-agent
```

---

### 11.3 B 模式验收

B 模式不能要求用户用：

```bash
/bio-gpu-team /path/to/biogpu_project.yaml
```

作为主流程。

B 模式必须问：

```text
1. 已有工程工作区在哪里？
2. 这次具体要做什么？
3. 是否允许修改已有 GPU 代码？
4. 是否需要确认 execution_plan.md？
```

然后写入：

```text
state/task_state.json.session_request
```

并生成：

```text
reports/execution_plan.md
```

### 11.4 agent 职责验收

```text
1. bio-gpu-benchmark-agent 负责自动查找/下载/初始化工具源码。

3. bio-gpu-test-runner-agent 只执行测试计划，不重新设计精度指标。
4. bio-gpu-existing-project-planner-agent 根据 session_request 生成 execution_plan.md。
```
